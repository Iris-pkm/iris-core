# Iris — Architecture Decision Log

Lightweight ADR format: Context → Decision → Rationale → Alternatives Considered → Status.

---

### ADR-001: Git-backed markdown vault as canonical source of truth
- **Context:** Needed durable, portable, lock-in-free storage for a personal knowledge base meant to outlive any single app version.
- **Decision:** Plain markdown files with YAML frontmatter, stored in a git repository, are the source of truth.
- **Rationale:** Portability, free versioning/history, human-readable even without Iris running, trivially backed up or synced by external tools.
- **Alternatives considered:** SQLite as source of truth (rejected — not portable or human-readable); proprietary binary format (rejected — lock-in).
- **Status:** Accepted.

### ADR-002: SQLite as derived, rebuildable cache — never a source of truth
- **Context:** Fast queries (search, relation lookups, view rendering) need indexed storage, but that shouldn't compromise the vault's portability.
- **Decision:** SQLite holds a fully derived cache, rebuildable from the vault at any time.
- **Rationale:** Keeps the vault as the single durable source of truth while still getting query performance.
- **Alternatives considered:** SQLite as primary store with markdown as export-only (rejected — inverts the ownership principle).
- **Status:** Accepted.

### ADR-003: Two-tier sync strategy
- **Context:** Real-time CRDT sync is complex to build correctly; naive sync is much faster to ship but weaker under concurrent edits.
- **Decision:** Ship naive WebSocket sync first (Phase A, with conflict-copy resolution — see ADR-012), layer CRDT-grade merge on later (Phase B).
- **Rationale:** Gets multi-device usable sooner without compromising on eventual correctness — Phase B isn't a "maybe," it's scheduled.
- **Alternatives considered:** Building CRDT from day one (rejected — delays everything else behind the hardest subsystem); sync via git alone with manual merges (rejected — too much friction for daily use); true last-write-wins with silent discard of the losing edit (rejected — see ADR-012, this is a real data-loss risk unacceptable for a second brain).
- **Status:** Accepted.

### ADR-004: Rust core + native/thin UI shells per platform
- **Context:** Target platforms are desktop (Win/Mac/Linux), mobile (iOS/Android), and tablet (iPad/Android tablet), with watch explicitly deferred. Solo dev, mixed language background, explicit preference for shared core logic + native UI shells over either a fully shared UI codebase or fully independent native builds.
- **Decision:** Single Rust core (vault engine, CRDT, search, plugin runtime, distillation logic) exposed via UniFFI/cxx bindings. Tauri for desktop UI, SwiftUI for iOS/iPad, Kotlin Compose for Android/tablet.
- **Rationale:** Correctness-critical logic is written and tested once. Each UI shell still feels native/idiomatic to its platform. The Rust core also gives WASM plugin sandboxing a natural home.
- **Alternatives considered:** Fully shared UI codebase (React Native/Flutter/KMP-Compose-Multiplatform) — rejected for feeling less native; fully native per-platform including business logic — rejected as unmaintainable for a solo long-haul build.
- **Status:** Accepted.

### ADR-005: BYO AI — provider-agnostic abstraction layer
- **Context:** The AI landscape shifts fast; betting on one provider risks obsolescence, and a personal vault holds sensitive content users may not want routed through a provider they didn't choose.
- **Decision:** AI is accessed via a provider-agnostic abstraction layer — user-supplied API key (Anthropic, Google, OpenAI, Deepseek, Qwen, etc.) or an MCP server connection for local models. The app is fully functional with zero AI configured.
- **Rationale:** Future-proofs against a shifting AI landscape; respects user trust decisions already made with their chosen provider; keeps AI as a genuine optional multiplier rather than a dependency.
- **Alternatives considered:** Single bundled AI provider (rejected — lock-in and trust concerns); no AI at all (rejected — distillation-assist is a key differentiator).
- **Status:** Accepted.

### ADR-006: Distillation queue trigger = project activation, not time-based scheduling
- **Context:** Time-based resurfacing (spaced repetition, daily review) doesn't match when knowledge actually becomes relevant.
- **Decision:** The distillation queue is triggered by a project moving to `active` status, surfacing that project's raw notes for progressive processing.
- **Rationale:** Relevance is project-driven, not calendar-driven — this is the mechanism that makes distillation feel just-in-time rather than a chore.
- **Alternatives considered:** Daily/weekly review reminders (rejected — same failure mode as existing tools); fully automatic distillation with no trigger (rejected — removes user agency and violates human-in-the-loop principle).
- **Status:** Accepted.

### ADR-007: Per-file `age` encryption for sensitive nodes — SUPERSEDED
- **Context:** Some vault content (e.g. journal entries) is more sensitive than the rest and shouldn't force all-or-nothing vault encryption.
- **Decision:** Per-file asymmetric encryption via `age`, opt-in per node.
- **Rationale:** Granular control without complicating the common case; keeps the vault mostly plain-text/portable while protecting what needs it.
- **Alternatives considered:** Whole-vault encryption (rejected — breaks portability and git diffability for non-sensitive content).
- **Status:** Superseded by ADR-011. Kept here for history rather than deleted — the reasoning about granularity was sound, but a follow-up session concluded the feature's actual functional cost outweighed the real-world threat it addressed. See ADR-011.

### ADR-008: GPL v3 as likely license for eventual open-source release
- **Context:** Interest in eventually sharing Iris beyond personal use, without a startup/business framing.
- **Decision:** Leaning toward GPL v3 as philosophically aligned (copyleft, keeps derivatives open).
- **Rationale:** Matches the no-lock-in, data-ownership ethos already baked into the architecture.
- **Alternatives considered:** MIT/Apache-2.0 (permissive — not yet ruled out, but less aligned with keeping derivatives open); proprietary (rejected — contradicts the project's own principles).
- **Status:** Leaning, not finalized.

### ADR-009: No gamification layer
- **Context:** XP, levels, achievements, streak-based rewards, and skill trees were explored in depth as a way to make Iris more motivating to use. Even a carefully redesigned "outcome-based" version (rewarding retrieval/traversal/completion instead of raw actions, specifically to resist Goodhart's-Law gaming) was still a viable design on the table.
- **Decision:** No gamification layer of any kind — no XP, no achievements, no levels, no skill trees, no quests.
- **Rationale:** Gamification exists to solve a motivation problem. Iris shouldn't have one by design — the distillation queue's just-in-time trigger, the daily note, and the search layers are meant to make using Iris its own reward. A parallel scoring system creates a second, app-specific goal (accumulate points) that competes with the real goal (better thinking), and works against several existing principles at once: correctness-over-metrics, depth-over-volume, and "the vault must outlive the app" (a points system is meaningless outside Iris and vanishes on export). Iris should earn daily use by being indispensable, not by manufacturing dopamine.
- **Alternatives considered:** Action-based XP (rejected — trivially gameable, rewards volume over depth); outcome-based XP rewarding retrieval/traversal/completion (rejected — still a parallel incentive system, and even a well-designed version is scope and complexity spent on a problem Iris shouldn't have).
- **What replaces it:** The non-gamified signals already in the design carry the motivational weight instead — the activity heatmap, plain streak tracking (no XP attached), and the Iris Score / analytics dashboard (reflects genuine vault health — graph density, distillation depth, retrieval rate — not points).
- **Status:** Accepted. Treat as a standing constraint on future feature proposals, not a one-time rejection — see `IRIS_PHASED_PRODUCT_PLAN.md` §11.7 ("Do Not Re-Propose Gamification") for the AI-collaborator-facing version of this rule.

### ADR-010: Lightweight-by-construction as a four-dimension performance model
- **Context:** Iris's feature surface is intentionally large (visualization, four-layer search, AI agent, sprints/timeline, widgets, browser extension, etc.). "Make it lightweight" needed a precise definition rather than a vague aspiration — one that couldn't be used as an excuse to cut features either.
- **Decision:** "Lightweight" means cost proportional to current usage, not to feature existence, decomposed into four independently-solved dimensions: **startup weight** (progressive/lazy loading — quick capture interactive in well under a second regardless of what else is loading), **memory weight** (lazy graph loading from the SQLite cache — never materialize the full graph or full embedding index in memory at once), **battery weight** (adaptive sync — aggressive in foreground, exponential backoff when backgrounded; background AI/embedding work gated on charging + WiFi), **storage weight** (git gc on a schedule; attachments never live in git history directly — content-addressed store instead; configurable history depth).
- **Rationale:** A feature a given user never touches (3D constellation view, AI layer, analytics dashboard) should cost that user nothing at rest. This is the engineering-level checklist form of the existing "zero-cost-when-unused" principle.
- **Alternatives considered:** Cutting feature scope to stay lightweight (rejected — conflates two different costs; the money/engineering-complexity cost of a feature existing is separate from the runtime cost of a feature being unused, and only the latter must be zero); optimizing later/reactively (rejected specifically for these four dimensions — retrofitting lazy-loading and adaptive sync into an already-built app is far more expensive than designing for it from Layer 0; one of the few places "optimization can be deferred" doesn't fully apply, since the *architecture* for cost-proportionality must exist early even if the tuning happens later).
- **Status:** Accepted. Applies to every new subsystem added after this ADR.

### ADR-011: No per-file encryption — rely on OS-level disk encryption instead
- **Context:** A follow-up review of ADR-007 surfaced that per-file `age` encryption has real, ongoing functional cost: encrypted nodes would drop out of the always-on search index (session-only re-indexing at best), git history degrades to opaque ciphertext blobs (defeating the version-diff/"watch my thinking evolve" feature for anything encrypted), AI features can't touch encrypted content without an explicit per-action unlock, frontmatter metadata (title, tags, relations) leaks unless separately redacted, and multi-device key management (getting the private identity to every device safely) adds real onboarding friction with a genuinely unforgiving failure mode — lose the passphrase, lose the notes, permanently.
- **Decision:** Drop per-file encryption entirely. Rely on OS-level full-disk encryption (FileVault/BitLocker/LUKS) as the baseline protection, same as most local-first note tools.
- **Rationale:** The realistic threat model for a personal vault is a lost/stolen device, which full-disk encryption already covers before Iris does anything. The specific content that would've used the feature (trading journal, personal reflections) is exactly the content most valuable to keep searchable and AI-queryable — encrypting it would defeat the reason it's in Iris at all. Precedent is telling: Obsidian ships no native per-note encryption in its core app (only paid Sync gets end-to-end encryption, and that protects data in transit, not notes at rest in the vault — per-note encryption exists only via community plugins), and Notion has no client-side or end-to-end encryption at all (server-side only, Notion holds the keys) — neither omission has been a blocker to either tool's adoption in this category.
- **Alternatives considered:** Keep ADR-007 as designed (rejected — cost outweighs a threat already covered by disk encryption); a lightweight app-level "hide from casual view" flag with no real cryptography (rejected for now as unnecessary complexity with no real protection behind it — nothing currently in Iris's design needs even that; revisit only if real usage surfaces a genuine need).
- **Status:** Accepted. `Phase 10 — Security and Private Vaults` in `IRIS_PHASED_PRODUCT_PLAN.md` is retired as a result (see that document for the note) rather than silently removed.

### ADR-012: Conflict copies instead of silent last-write-wins
- **Context:** Phase A naive sync was originally described as "last-write-wins," which — taken literally — means that when the same node is edited independently on two devices before syncing (e.g. offline edits on a phone and a laptop that later both come online), the edit that syncs second silently overwrites and discards the other. This was flagged as an open thread ("sync conflict UX") from the earliest version of these docs and never resolved.
- **Decision:** On a detected conflict, Iris never silently discards either version. The version that syncs first becomes the canonical node; the other is preserved as a separate node — tagged `conflicted`, linked back to the original via a typed relation — and surfaced via a small badge/list until the user reconciles it (copy content across, discard, or merge manually). Analogous to a GitHub merge conflict in spirit (two edits from a common ancestor need reconciling), but resolved by keeping two clean, complete, side-by-side versions rather than splicing inline conflict markers into the file.
- **Rationale:** This is the direct operational consequence of the standing principle "losing or corrupting notes is unacceptable" (see `IRIS_PHASED_PRODUCT_PLAN.md`) applied specifically to sync — it makes even the naive Phase A implementation safe against silent data loss, without needing to wait for CRDT-grade merge (Phase B) to get that guarantee. It's also considerably cheaper to build now than either full CRDT merge or a git-style inline merge UI.
- **Alternatives considered:** True last-write-wins with silent discard (rejected — the actual data-loss risk this ADR exists to close); inline text-merge-marker UI in the style of git conflict markers (rejected — too technical for non-code content, and Iris's node model doesn't map cleanly onto line-based diff markers the way source code does); blocking sync entirely until a conflict is manually resolved before either device can proceed (rejected — disproportionate friction for how rare conflicts actually are in single-user use, and defeats the point of background sync).
- **Status:** Accepted, effective from Phase A onward. The CRDT layer (Phase B) reduces how often conflicts occur in the first place, but conflict-copy surfacing remains the fallback for anything it can't auto-merge (e.g. structural/relation-level conflicts, not just text).

### ADR-013: No telemetry
- **Context:** The privacy/telemetry stance was implied by local-first + no-lock-in + eventual open-source, but never stated explicitly. It's exactly the kind of commitment that should be on the record rather than assumed, both for the developer's own clarity and because it's the first thing someone auditing an open-source personal-knowledge tool checks.
- **Decision:** Iris sends zero telemetry, has no phone-home of any kind, and collects no server-side usage analytics. If crash reporting is ever added, it is strictly opt-in and scrubbed to stack traces only — never vault content, never file paths, never node text.
- **Rationale:** A second brain holds a person's most sensitive raw thinking. Any background transmission is inconsistent with the trust the tool is asking for and with the local-first principle already established. The cost of *not* collecting telemetry (harder to debug issues remotely) is acceptable for a personal/open-source tool and is partially offset by the user-facing vault integrity checker and opt-in crash reports.
- **Alternatives considered:** Anonymous/aggregate usage analytics on by default with opt-out (rejected — "on by default" is precisely the pattern the privacy stance exists to reject, regardless of anonymization claims); no crash reporting at all, ever (not chosen as a hard rule — opt-in, content-scrubbed crash reports are a reasonable future option that doesn't compromise the principle).
- **Status:** Accepted.

### ADR-014: Single active vault (multi-vault allowed on disk, one active at a time)
- **Context:** The question of whether Iris supports multiple vaults surfaced from the roadmap's ambiguous "Vault picker" wording. Iris's whole premise — one connected graph, one search index, one AI context, cross-domain links — is undermined if a user's knowledge is split across multiple simultaneously-active vaults.
- **Decision:** Iris operates on exactly one **active** vault at a time. The graph, all four search layers, the AI's context, and analytics operate exclusively over that one vault; there is never cross-vault traversal, search, or AI reasoning. The app is not, however, hardcoded to know about only one vault folder ever — switching vaults is supported as a deliberate, heavyweight operation (close current vault, point at a different folder, rebuild the cache from scratch).
- **Rationale:** Preserves the "everything connects" thesis while still permitting the legitimate exceptional cases for a second vault folder: a sandbox for testing a plugin or risky schema change without endangering the real vault, and a parallel vault during a structural migration. The critical distinction, easy to conflate: a **Space** switch is an instant, lightweight context change *within* the one open vault; a **vault** switch closes one graph and opens another. "Vault picker" therefore means "point Iris at a vault folder" (first-run, restore-from-backup, or the rare deliberate switch), not "routinely choose among many vaults" — implemented as a lightweight "recent vaults" list in the VS Code / Obsidian workspace-folder style.
- **Alternatives considered:** True multi-vault with simultaneous cross-vault linking/search (rejected — fragments the graph and defeats the core premise; if two bodies of knowledge should link, they belong in one vault); strictly one vault folder ever, no switching at all (rejected — needlessly forecloses the sandbox and migration use cases at no real benefit).
- **Status:** Accepted. See `ARCHITECTURE.md` §6 (Multi-vault behavior) for the full treatment.

### ADR-015: Reminders are manual-only
- **Context:** When designing notifications/reminders, the initial sketch had Iris auto-generating notifications from task due dates, event start times, sprint deadlines, and streak-at-risk conditions. On reflection this is the same "the system decides when to interrupt you" pattern that manufactured-urgency gamification was rejected for (ADR-009).
- **Decision:** Reminders are a user-authored `reminder` node type and are manual-only: the reminder text is always written by the user (never auto-generated from another node's title), and a reminder never fires unless the user explicitly created it. Task due dates, event start times, sprint-ending, and streak-at-risk remain *in-app indicators only* (Today view, burndown, streak counter) and never push an OS notification on their own. A user who wants to be nudged about a due task creates a reminder for it themselves — optionally one tap from the task (pre-filling the task's title as an *editable* starting point), but never automatically.
- **Rationale:** Iris surfaces state; it interrupts the user only when explicitly asked to. This keeps the app from making unilateral decisions about what deserves the user's attention, consistent with the same philosophy that rejected gamification's engineered nudges. It also happens to be simpler and more predictable than a rules engine deciding when to fire.
- **Alternatives considered:** Auto-generated notifications from due dates/events/sprints (rejected — unilateral interruption, the ADR-009 pattern); a hybrid where some categories auto-notify and others are manual (rejected — inconsistent and hard to reason about; the clean rule is "nothing notifies unless you made a reminder"). Delivery is OS-native local scheduling (no server, no polling loop) to stay consistent with the battery-weight dimension of ADR-010.
- **Status:** Accepted.

### ADR-016: Archive is lifecycle state, not a node type
- **Context:** The node-type list originally included `archive` as a type. External review (see `IRIS_DOCUMENT_REVIEW_AND_VERDICT.md`) correctly pointed out that an archived project is still a *project*, an archived note still a *note* — changing `type` to `archive` on archival would destroy or obscure the node's original semantics, which is exactly wrong for a long-lived, user-owned vault.
- **Decision:** Remove `archive` from the built-in node types. Archival becomes lifecycle metadata carried by any node, orthogonal to its type: a `lifecycle` field (`active | archived`) plus an `archived_at` timestamp, sitting alongside the existing `deleted_at` (Trash) marker. The node's `type` never changes. "Archive" becomes a *system view* (filter for `lifecycle: archived`), not a container type. The PARA "Archive" concept is thus expressed as state, not as a distinct kind of thing.
- **Rationale:** Preserves each node's true semantics permanently; makes "archived" and "trashed" cleanly distinct lifecycle states rather than conflating type with status; and means un-archiving is a trivial state flip rather than a type migration. Three lifecycle-ish states now exist and are deliberately distinct: **active** (normal), **archived** (preserved but inactive — `archived_at` set), **trashed** (recoverable, pending removal — `deleted_at` set); hard-deletion (git-history-only) remains the terminal state beyond Trash.
- **Alternatives considered:** Keep `archive` as a type (rejected — destroys original semantics); a single `status` enum mixing active/archived/trashed (rejected — trashed is a different concern from archived, and `deleted_at` already exists; two orthogonal timestamps model it more precisely than one overloaded enum).
- **Status:** Accepted. `SCHEMA_SPEC.md` and `ARCHITECTURE.md` §3/§4 updated accordingly.

### ADR-017: Relations stored in one canonical direction; inverses derived via a registry
- **Context:** The schema listed both `blocks` and `blocked-by` (and similar pairs) as storable relation types. If both can be written independently to files, contradictory states become representable (A says it blocks B; B doesn't say it's blocked by A), and there's no single source of truth for the edge.
- **Decision:** Each relationship is persisted on exactly **one** canonical side, in one canonical direction. The inverse is never stored — it's computed by the engine from a defined **inverse registry** that maps each canonical relation type to its inverse label. E.g. `blocks` is canonical and stored; `blocked-by` is a derived, query-time/UI-only inverse and is never written to a file. Same for `parent`→`children`, `references`→`referenced-by`, `annotates`→`annotated-by`, etc.
- **Rationale:** Makes contradictory relation states unrepresentable by construction (there is only one edge, stored once), consistent with the derived-backlinks principle already in the architecture. The inverse registry gives the UI and query engine full bidirectional navigation without duplicating — or risking desyncing — the underlying data.
- **Alternatives considered:** Store both directions and reconcile on read (rejected — reconciliation logic is a bug farm, and "which side wins on conflict" is an unnecessary question); store both and treat them as independent (rejected — the contradictory-state problem this ADR exists to close).
- **Status:** Accepted. `SCHEMA_SPEC.md` §5 updated with the canonical-direction rule and the inverse registry.

### ADR-018: Explicit project lifecycle state machine
- **Context:** Project status appeared with varying vocabularies across docs (`someday`/`active`/`complete` in some places, plus `paused`, `planned`, `archived`, `cancelled` implied elsewhere). Because a project transitioning to `active` is what triggers the distillation queue (ADR-006), this state machine cannot be vague — the trigger semantics depend on it.
- **Decision:** Adopt an explicit state machine. States: `someday → planned → active → paused → active`, `active → completed`, `planned → cancelled`, `paused → cancelled`, `completed → archived` (via lifecycle, ADR-016), `cancelled → archived`. Distillation-queue trigger rules are pinned precisely: (1) activation fires on any transition from a non-active state *into* `active`; (2) it does **not** re-fire merely on opening/viewing an already-active project; (3) while a project remains `active`, newly-linked raw notes are added to its queue incrementally — so activation is a continuously-maintained membership, not a one-time snapshot. Rule (3) closes a real hole the review caught: without it, notes linked after activation would never enter the queue.
- **Rationale:** Makes the product's defining mechanism (relevance-triggered distillation) deterministic and implementable; removes cross-doc vocabulary drift; and the "archived" terminal state now routes through the lifecycle model (ADR-016) rather than being a project-specific status, keeping concerns separate.
- **Alternatives considered:** Leave status as a free/loose enum (rejected — the distillation trigger needs precise semantics); model activation as a one-time snapshot (rejected — later-linked notes would silently never distill).
- **Status:** Accepted. Reflected in `SCHEMA_SPEC.md` (project type) and `ARCHITECTURE.md` §11.

### ADR-019: Lossless frontmatter editing; body and user formatting preserved
- **Context:** The testing strategy requires parse→serialize to be byte-identical ("files are canonical"). But ordinary YAML serializers rewrite key order, quote style, spacing, comments, and list syntax — so a naive parse→mutate→write would produce noisy diffs and could discard user comments/formatting in hand-edited files. Two designs are possible: lossless editing (mutate only the changed fields in place, preserving everything else) vs. canonical serialization (normalize the whole file to one deterministic format on every save).
- **Decision:** Iris uses **lossless frontmatter mutation with full body preservation**. When Iris changes a node, it edits only the specific frontmatter fields that actually changed, leaving key order, comments, whitespace, unknown fields, and the entire Markdown body byte-for-byte untouched. It does not re-serialize the whole file from an in-memory model.
- **Rationale:** Respects that files are canonical and hand-editable — a user's manual formatting and comments survive Iris touching the file; git diffs stay minimal and meaningful (only real changes show); and it composes with the "preserve unknown fields/types" rule (a file written by a newer or plugin-extended Iris isn't damaged by an older one). This materially shapes parser architecture — it implies a concrete-syntax-tree / span-preserving editor rather than a load-model-then-dump serializer — which is exactly why it's decided before any parser code exists.
- **Alternatives considered:** Canonical serialization / normalize-on-save (rejected — simpler to build, but rewrites user formatting, can drop comments, and produces noisy first-save diffs; the wrong trade for a canonical-files, hand-editable vault); byte-identical only for untouched files but full re-serialize on edit (rejected — still loses formatting/comments on any edited file).
- **Status:** Accepted. Noted in `SCHEMA_SPEC.md` and `ARCHITECTURE.md` §5/§16; the golden-file round-trip tests assert lossless behavior on *edited* files, not just untouched ones.

### ADR-020: The canonical vault is the Markdown repo **plus** the content-addressed blob store
- **Context:** The vault is git-backed and canonical, but large binary attachments are deliberately kept out of ordinary git history (they'd bloat it) and may sync via a separate mechanism. This raised a foundational question the review sharpened: is a plain `git clone` sufficient to reconstruct the *complete* vault? If attachments live outside git history, then no — git alone is only the text/metadata layer.
- **Decision:** The canonical vault is explicitly defined as **the Markdown/git repository *and* the content-addressed blob store, together**. Neither alone is the complete vault. The vault manifest tracks which blobs are required (by hash); the integrity checker reports missing attachments; and backup/restore must include *both* the node files and the blob content to be considered complete. Attachments are first-class canonical data, not external references.
- **Rationale:** Removes ambiguity about what "the vault" is and what a complete backup must contain — critical for the data-ownership and restore guarantees. It's honest about git's role (canonical *text and metadata* layer) without pretending attachments are second-class or disposable.
- **Alternatives considered:** Git+LFS as the single canonical unit (viable, but couples the blob strategy tightly to git/LFS tooling; rejected as the *definition* though LFS may still be an implementation option for the blob transfer); attachments as external references not guaranteed in backup (rejected outright — breaks the ownership/portability promise).
- **Status:** Accepted. `ARCHITECTURE.md` §5 and `SCHEMA_SPEC.md` §8 updated; restore semantics (first-run restore, `ARCHITECTURE.md` §5) must fetch both repo and blobs before declaring completion.

### ADR-021: Canonical-write-wins transaction ordering across filesystem, SQLite, and git
- **Context:** A single node edit touches three systems: the canonical Markdown file, the derived SQLite cache, and git history. Without an explicit ordering and failure policy, a partial failure could corrupt the cache, leave partial multi-file writes, or — worst — discard the user's actual content because a *secondary* system failed.
- **Decision:** Canonical filesystem state is always authoritative, and the write order is fixed: (1) validate the intended mutation; (2) atomically write the canonical file(s); (3) update or, on any doubt, rebuild the affected cache records; (4) create the git commit per commit policy; (5) if the cache update fails, mark the cache dirty and rebuild rather than trusting a partial update; (6) if the git commit fails, retain the canonical data and surface an "unsaved history" warning rather than reverting the file. **Core rule: a canonical file mutation is never rolled back solely because SQLite or git failed** — the cache is rebuildable and a commit can be retried, but the user's canonical content must never be discarded because a secondary system errored. Multi-file operations must not leave partial canonical mutations (atomicity at the canonical layer).
- **Rationale:** Directly protects the thing that matters most (the user's actual notes) against failures in the two systems that exist only to *serve* those notes. Falls straight out of "files are canonical; SQLite is a rebuildable cache" (ADR-001/002) but needed to be stated as an operational contract, not just a data-model stance.
- **Alternatives considered:** Treat all three systems as a single distributed transaction that rolls back together (rejected — would let a git or SQLite failure discard real user content, inverting the priority); update cache first then file (rejected — cache must never lead the canonical state).
- **Status:** Accepted. To be honored by the core engine's write path from the first CRUD implementation; the CRUD test harness must cover partial-failure cases (see `ARCHITECTURE.md` §16 and the review's required-test-coverage list).

### ADR-022: Vault-wide OCR indexing — on-device by default, optional cloud provider
- **Context:** Evernote's single most-defended, best-in-class capability is OCR that extracts text from *every* image, PDF, scan, and handwritten note in the vault and folds it into search — so a word appearing only inside a chart screenshot or a scanned receipt is still findable. Iris's design had OCR only in two narrow spots (camera-to-node capture, and the ink-note transcript); it had no general "OCR every attachment → make it searchable" capability. This is a genuine retrieval gap against the one tool still clearly ahead here, and retrieval is core to Iris's thesis.
- **Decision:** Add vault-wide OCR indexing. Every image/PDF/scan attachment (and ink-note strokes) is OCR'd; the extracted text is folded into the search layers (lexical directly; semantic via embeddings if configured) and stored as derived, cached data — never mutating the canonical attachment or node body. **OCR runs on-device by default** (a bundled local OCR engine), consistent with local-first, zero-telemetry (ADR-013), and works-without-AI. A user may *optionally* configure a cloud OCR provider through the same BYO abstraction as the AI layer (ADR-005) when they want higher accuracy and accept sending image content to that provider — an explicit, per-user choice, never a default or a requirement.
- **Rationale:** Closes the most meaningful capture/retrieval gap versus Evernote while staying true to Iris's principles — on-device keeps it private and dependency-free; the optional cloud path gives power users Evernote-grade accuracy without compromising anyone who wants everything local. Framed as *feeding the node/search substrate* (an OCR'd scan is a searchable, linkable, distillable node), not as a parallel Evernote-style filing feature — honoring guardrail 6.10.
- **Cost/placement:** OCR is compute-heavy, so it obeys the battery-weight rule (ADR-010) — batched, gated on charging/WiFi where appropriate, run in the background, never blocking capture. Extracted text is derived cache (rebuildable, like the rest of the index), so it obeys the storage-weight rule too. The OCR'd-but-not-yet-indexed window is surfaced the same way pending semantic indexing is (`ARCHITECTURE.md` §15).
- **Alternatives considered:** Keep OCR narrow/capture-only (rejected — leaves the retrieval gap open, and "I can't find the note with that diagram in it" is a real daily failure); cloud-only OCR for quality (rejected — violates local-first and no-telemetry defaults; only acceptable as an opt-in); no OCR at all (rejected — cedes the one area Evernote is genuinely best at, in a category central to Iris).
- **Status:** Accepted. Builds on the attachment model (`ARCHITECTURE.md` §5) and search (§15). The document scanner (edge detection / perspective correction / multi-page) and in-image search-term highlighting are downstream extensions enabled by this, specified in `OVERVIEW.md` and `PRD.md`.

### ADR-023: Guided project activation is a first-class capability, not just a status change
- **Context:** Project activation is Iris's core differentiator (ADR-006/ADR-018 — activating a project triggers the distillation queue). But in the docs so far, activation was described mechanically: it flips a status and enqueues raw notes. External adoption review (`IRIS_MISSING_PRODUCT_CAPABILITIES.md` §5, and its "Core Product Test") argued — correctly — that the mechanism undersells the moment. The decisive question for whether Iris deserves to exist is: *when a user activates a project, does Iris bring together the knowledge, actions, context, and next steps they need better than the tools they already use?* A status flip doesn't answer that; an assembled working environment does.
- **Decision:** Elevate activation from "trigger the distillation queue" to assembling a **focused working environment**. On a project entering `active`, Iris surfaces, in one activation view: (1) linked raw/undistilled notes (the existing queue), (2) unresolved decisions linked to the project, (3) dependent and blocked tasks, (4) related resources, (5) upcoming calendar constraints touching the project, (6) recently-added related material, and (7) a recommended starting set of next actions. Everything shown is derived from data already in the graph (relations, task states, distillation levels, calendar events) — activation is a *query and presentation* layer over the substrate, not new stored state, honoring guardrail 6.10 (attach to substrate, don't build a parallel system).
- **Rationale:** This is the single feature the adoption review identifies as make-or-break, and it's the tangible expression of the whole "resurface the right knowledge when work becomes active" thesis. Framing it as an environment rather than a trigger is what makes the differentiator *visible in everyday use* rather than buried in a status field. It also composes cleanly with ADR-018's incremental-queue rule (notes linked while active keep flowing into the environment) and with transparent retrieval (ADR-024) — each surfaced item can explain why it's there.
- **AI boundary:** the *recommended starting actions* are the one element that benefits from AI (ranking/suggesting what to tackle first). Per the same manual-first discipline applied to distillation (roadmap §Phase 2/4), the activation environment must be fully useful with **zero AI configured** — without AI it surfaces and groups the linked material and lets the user choose; with AI it additionally *recommends* an ordered starting set. AI enriches, never gates.
- **Alternatives considered:** Keep activation as a status flip that only feeds the distillation queue (rejected — mechanically correct but fails the Core Product Test; the differentiator stays invisible); make the activation environment an AI-generated summary (rejected — would make the core differentiator depend on AI, violating "AI optional, never load-bearing," ADR-005).
- **Status:** Accepted. Specified in `ARCHITECTURE.md` §11.5 (Guided Project Activation) and surfaced in `OVERVIEW.md`, `PRD.md`, and the roadmap's distillation/planning phases.

### ADR-024: Transparent retrieval — results explain why they surfaced
- **Context:** Iris's search fuses four layers via RRF (ADR/§15) plus OCR'd content, active-project relevance, backlinks, distillation level, recency, etc. That's powerful but risks being an opaque ranker — the user sees an ordering and has to trust it. The adoption review (§8) argued users should *trust retrieval because the relevance is understandable*, not because a model ranked it — which is squarely in line with Iris's anti-black-box, honest-signals ethos (cf. the diagnostic-panel-over-single-score reasoning in ADR-009-adjacent design).
- **Decision:** Every surfaced result can explain *why* it appeared. A result carries its contributing signals — matched terms, title/metadata match, project/area/resource relationship, backlink relevance, recent usage, distillation level, active-project relevance, OCR source, attachment source, semantic similarity, temporal relevance — and the UI can show a compact "why this?" rationale (e.g. "Linked to Project Iris · contains 'lossless YAML' · referenced by 2 active tasks · distillation: highlighted"). Because RRF already combines *ranked signals*, the contributing signals are available at ranking time; exposing them is a presentation choice, not new infrastructure.
- **Rationale:** Turns retrieval from "trust the model" into "see the reasoning," consistent with Iris's broader stance that the system should surface understandable signals rather than opaque scores. Also genuinely useful: a visible rationale helps the user refine what they're looking for, and helps them notice when a link or distillation level is doing useful work.
- **Alternatives considered:** Opaque ranked list only (rejected — cedes the trust advantage a local, inspectable system should have); always-on verbose explanations (rejected — noisy; the rationale is available on demand / compact by default).
- **Status:** Accepted. Noted in `ARCHITECTURE.md` §15 and `OVERVIEW.md` search section.

### ADR-025: Migration/import is onboarding-critical, not a late utility
- **Context:** The docs listed "import from Obsidian/Notion/Roam/markdown" as a Meta/System feature — implicitly a nice-to-have to build eventually. Adoption review (`IRIS_MISSING_PRODUCT_CAPABILITIES.md` §2) made the sharper point: *nobody abandons years of accumulated notes to start empty.* For any serious user, the ability to move their existing vault in — preserving links, attachments, tags, timestamps, task states, hierarchy — is a *precondition for adoption*, not a later convenience. Treating it as a late utility means the product can't actually be adopted by the exact people most likely to want it.
- **Decision:** Reframe migration/import as an onboarding-critical capability. First-run offers "import from…" alongside create/open/restore. Supported sources (in rough priority): Obsidian vaults (preserve wikilinks → Iris relations, frontmatter, attachments), plain Markdown folders (the safest universal path), Notion export (databases → node types, page properties → frontmatter), Evernote ENEX (notes + attachments + created/modified timestamps + tags — pairs naturally with the OCR/Evernote-parity work in ADR-022), Roam JSON, task CSV (Todoist/generic), calendar ICS, and browser bookmarks. Import preserves as much as technically possible: internal links, attachments, dates, tags, folder hierarchy, task states, page properties, aliases, source references, embedded files, existing frontmatter, and creation/modification timestamps.
- **Rationale:** Migration quality directly gates who can adopt Iris at all. Because Iris's canonical format is plain Markdown + YAML frontmatter, importing *from* Markdown-family tools (Obsidian, plain MD) is high-fidelity and low-risk; the harder imports (Notion's database model, ENEX) are where real mapping work lives, but they're also where the most switchable users are. Framing it as onboarding (not a someday Meta feature) forces it into the adoption path where it belongs.
- **Sequencing note:** the *first* importer to build is plain-Markdown-folder + Obsidian, because they map most directly onto Iris's own format and validate the import pipeline with the least mapping complexity; ENEX/Notion follow. This lands in the roadmap's foundation/desktop stages, not deferred to a late phase.
- **Alternatives considered:** Keep import as a late Meta feature (rejected — makes the product un-adoptable for its target user until "late"); build a single universal importer (rejected — each source has genuinely different semantics; a shared core with per-source adapters is the right shape); import-by-reference without copying into the vault (rejected — breaks the canonical-vault/ownership model, ADR-020).
- **Status:** Accepted. Reflected in `OVERVIEW.md` (Meta → onboarding), `PRD.md` requirements, and the roadmap (import in the desktop-foundation stage, not deferred).

### ADR-026: Templates are three distinct tiers, not one fuzzy feature
- **Context:** "Templates" appeared across the docs meaning at least three different things — a starter page, the Figma-style live-linked Components/Instances mechanism, and the adoption review's "starter systems" (whole configured workflows) — with no single place defining them, and no clean line between the simplest tier (copy-on-use) and the live-linked tier. This fuzziness is a real risk: templates are an adoption lever (the review called out starter *systems* specifically), and an underspecified template model tends to collapse into "just a starter page," losing the more powerful tiers, or conversely to over-engineer the simple case. This ADR pins the model down as three explicitly distinct tiers with different mechanics, different build phases, and different purposes.
- **Decision:** Iris has **three tiers of template**, treated as separate concepts that happen to share a word:

  **Tier 1 — Node templates (copy-on-use).** A reusable starting point for a *single* node: a daily-note layout, a meeting-note skeleton, a book-review structure. Mechanically the simplest possible thing — a node flagged as a template (e.g. `is_template: true` in frontmatter, excluded from normal views/search), **copied** when used. The copy is fully independent; later edits to the template do **not** affect notes already created from it. This is the "template" most apps mean, and it's the early, easy tier. No `instance-of` relation is created — it's a one-time copy.

  **Tier 2 — Components / Instances (live-linked).** A template node acting as a **Component**; every node created from it is an **Instance** carrying an `instance-of` relation (SCHEMA_SPEC §5) back to the Component. The Instance inherits the Component's schema but can override individual fields locally. Editing the Component (e.g. adding a field) **propagates** to every Instance that hasn't overridden that specific field — the live-linked relationship Figma has between components and instances. This is the mechanism behind schema evolution ("add a field to every trading-journal entry" becomes a template edit, not a manual migration). Distinct from Tier 1 precisely because the link persists and changes propagate. Override semantics remain an open sub-question (see Open list).

  **Tier 3 — Starter systems (configured workflows).** The adoption-review sense: not a page but a *whole working setup* for a domain (software project, research paper, trading journal, reading pipeline, job search, fitness plan…). A starter system may bundle node types, relations, views, statuses/workflow states, activation behavior, dashboards, default queries, capture destinations, and review workflows — installed as a unit so a non-builder adopts a sophisticated workflow without designing it. Tier 3 is built *on top of* Tiers 1–2 plus custom node types (the plugin/custom-type system), which is why it lands latest.

- **Rationale:** Naming the three tiers separately prevents the collapse-to-starter-page failure and the over-engineer-the-simple-case failure at once. It also maps cleanly onto build order: Tier 1 is cheap and early (Desktop phase), Tier 2 rides on the Components/Instances mechanism and custom types (Plugin phase), Tier 3 rides on Tier 2 + custom types + views (Plugin phase and beyond). Each tier attaches to the node/relation substrate rather than introducing a parallel system (guardrail 6.10): a template *is* a node; a starter system is a bundle of nodes, relations, and view configs.
- **AI boundary:** none required. All three tiers are fully mechanical (copy, inherit-with-override, bundle-install). AI could later *suggest* a starter system based on how a user works, but no tier depends on AI.
- **Alternatives considered:** One unified "template" concept (rejected — the copy-on-use and live-linked mechanics are genuinely different, and users need to know which they're getting; conflating them causes "why did editing this change my old notes?" surprises); only Tier 1 (rejected — cedes schema-evolution and the adoption-critical starter-systems lever); building Tier 3 as bespoke first-party bundles hardcoded in the app (rejected — starter systems should be defined in the same declarative form users/plugins can author, not privileged app internals).
- **Status:** Accepted. Fully specified in `ARCHITECTURE.md` §4 (template tiers) and surfaced coherently in `OVERVIEW.md`, `PRD.md`, `SCHEMA_SPEC.md` (the `is_template` flag and `instance-of` relation), and the roadmap (Tier 1 → Desktop; Tiers 2–3 → Plugin phase).
